Por que mostramos os bastidores

Um sistema bom não começa no código: começa no papel. Antes de programar o Ouro do Norte, a gente parou para entender o problema, listar o que o sistema precisava fazer e desenhar como as informações iriam circular. Essa parte da análise é pouco visível para quem usa o sistema, mas é ela que evita retrabalho e erro lá na frente.

Na prática, cada diagrama respondeu a uma pergunta. Os eventos e os casos de uso disseram o que acontece e quem faz o quê. O fluxo de dados mostrou de onde cada informação vem e para onde vai. O diagrama de classes organizou as peças do sistema e o modelo do banco de dados definiu onde cada dado fica guardado.

Por isso, quando chegou a hora de programar, a equipe já sabia o que construir: o código seguiu o desenho, as telas seguiram os casos de uso e o banco de dados já nasceu organizado. É esse jeito de trabalhar que a gente leva para os projetos dos nossos clientes.

Análise

Análise: o que o sistema precisa fazer

Primeiro entendemos o que acontece no dia a dia e quem participa.

Eventos do sistema

Mapeamos tudo o que acontece com o sistema, do acesso do funcionário à gestão dos parâmetros. São nove eventos, e cada um virou uma parte do sistema.

  • E01Funcionário acessa o sistema
  • E02Funcionário gerencia lote
  • E03Sistema calcula validade e valor
  • E04Funcionário gera e imprime etiqueta
  • E05Funcionário consulta histórico
  • E06Funcionário solicita reimpressão
  • E07Funcionário solicita cancelamento
  • E08Sistema identifica vencimento
  • E09Administrador gerencia parâmetros

Casos de uso (UML)

O diagrama mostra 17 casos de uso, ou seja, 17 coisas que alguém consegue fazer no sistema, e quem participa de cada uma: o funcionário, o gerente (que herda tudo o que o funcionário faz) e a impressora. Ele serviu de lista de telas e funções.

Fluxo de dados

Fluxo de dados (DFD)

Para onde cada informação vai, e por onde passa até ficar guardada.

DFD de contexto

A visão mais simples: o sistema no centro e quem conversa com ele (funcionário, administrador e impressora), com as informações que entram e saem.

DFD de nível 0

Abre o sistema por dentro: 5 processos (acesso, lote, etiqueta, histórico e administração) e 4 depósitos onde os dados ficam guardados. É o mapa que mostra o caminho de cada dado.

Classes

Diagrama de classes

As peças do sistema e como elas se encaixam.

Organizando as peças

O diagrama de classes organiza o sistema em Funcionário, Gerente, Produto, Lote, Etiqueta, Impressora, Histórico de Etiquetas e Parâmetros do Sistema, com o que cada peça guarda e o que cada uma sabe fazer. É a ponte entre o desenho e o código.

Banco de dados

Modelo entidade-relacionamento

Por fim, o modelo do banco de dados define as 7 tabelas que guardam tudo e como elas se ligam. É o trabalho de organização de dados que sustenta o sistema inteiro.

As 7 entidades

Cada cartão é uma tabela. PK marca a chave primária (o identificador) e FK marca a chave estrangeira (a ligação com outra tabela).

Usuário

USUARIO

Funcionários e gerentes que acessam o sistema. O campo perfil define o que cada um pode fazer.

  • id_usuarioPK
  • nome
  • email
  • senha
  • perfil

Categoria de produto

CATEGORIA_PRODUTO

Agrupa os produtos e guarda o prazo de validade em dias, usado no cálculo da validade.

  • id_categoriaPK
  • nome_categoria
  • prazo_validade_dias

Produto

PRODUTO

Cada item que recebe etiqueta. Todo produto pertence a uma categoria.

  • id_produtoPK
  • codigo_produto
  • nome_produto
  • id_categoriaFK

Lote

LOTE

Um produto embalado em uma data, com peso líquido, tara, preço por kg e validade.

  • id_lotePK
  • codigo_lote
  • peso_liquido
  • tara
  • preco_por_kg
  • data_embalagem
  • data_validade
  • id_produtoFK
  • id_usuario_cadastroFK

Etiqueta

ETIQUETA

Etiqueta gerada a partir de um lote, com seu status e a data de geração.

  • id_etiquetaPK
  • status
  • data_geracao
  • id_loteFK

Impressora

IMPRESSORA

Impressoras cadastradas. O campo ativa mostra se ela está em uso.

  • id_impressoraPK
  • nome_impressora
  • identificador
  • ativa

Histórico de etiqueta

HISTORICO_ETIQUETA

Registro de cada ação sobre uma etiqueta: quem fez, quando, em qual impressora, quantas cópias e o motivo.

  • id_historicoPK
  • id_etiquetaFK
  • id_usuarioFK
  • id_impressoraFK
  • tipo_acao
  • data_hora
  • quantidade_copias
  • motivo

Como as tabelas se ligam

Lemos cada linha da esquerda para a direita.

  • Categoriaclassifica vários produtos. Cada produto tem uma só categoria.1 : N
  • Produtopode ter vários lotes. Cada lote é de um único produto.1 : N
  • Usuáriocadastra vários lotes. Cada lote guarda quem o cadastrou.1 : N
  • Lotegera várias etiquetas. Cada etiqueta vem de um só lote.1 : N
  • Etiquetatem pelo menos um registro no histórico.1 : N
  • Usuáriorealiza várias ações. Todo registro do histórico tem um usuário.1 : N
